## 2026-04-22

### 问题：任务分级速查表失踪
- **发现**：全系统自检发现 SKILL.md 中无 L1-L4 分级规则文档
- **修正**：在 SKILL.md「双模式分流」章节后补入 L1-L4 速查表
- **原则**：Phase 1 完成的功能必须同步到主文件，不能只记在 MEMORY.md 里

### 问题：部门交接格式不统一
- **发现**：SKILL.md 要求所有部门输出含 `task_id/status/summary/next_action`，但11个角色卡均未定义 `task_id` 字段
- **修正**：SKILL.md 改为明确「正文在前，交接4字段在末尾」，不强制JSON格式，各部门自便
- **原则**：交接格式规范写在 SKILL.md，不分散在各部门角色卡里

### 问题：Mode B 部门卡加载时机不明
- **发现**：SKILL.md 说「构建spawn时注入角色卡」，但没说何时读、读几张
- **修正**：SKILL.md 并行派发步骤改为：识别部门 → 加载角色卡（≤4张）→ 直接构建spawn
- **原则**：操作步骤必须完整，不能留「到时候知道」这种模糊点

### 问题：通商部信息来源选择无具体规则
- **发现**：「去对的地方」过于抽象，每次都要自己判断
- **修正**：通商部角色卡新增「信息来源速查表」，按任务类型给出首选/备用/禁忌
- **原则**：决策规则必须有具体条件，不能只给方向

### 问题：工部超时重试逻辑缺失
- **发现**：调度器说「3次重试仍失败→停止」，但工部角色卡无对应说明
- **修正**：工部角色卡加「超时重试规范」+「技术选型偏好」
- **原则**：调度器的规范必须同步到对应执行部门的角色卡里，不能只写在一处

### 问题：依赖注入机制缺失
- **发现**：调度器场景B说「结论注入下游」，但没有说明注入步骤
- **修正**：调度器 Step 2 新增「依赖注入规范」：三步注入 + 上游超时处理
- **原则**：跨部门协作的接口必须显式定义，不能靠「调度器知道」

### 问题：枢密院超时在 SKILL.md 未体现
- **发现**：调度器内部写了枢密院超时→停止，但 SKILL.md 错误处理没提
- **修正**：SKILL.md 错误处理章节加「枢密院超时→停止整个任务」
- **原则**：调度器里的关键规则必须在 SKILL.md 有对应引用

## 2026-04-24 架构审查修复

### 问题：工部超时仍是瓶颈
- **发现**：300s只够完成架构阶段，代码实现永远跑不完
- **修正**：工部角色卡明确两阶段时间分配（架构90s + 实现210s），调度器增加partial处理逻辑
- **原则**：复杂任务必须分阶段，每阶段有明确交付物和超时底线

### 问题：审核链过重
- **发现**：三级串审（刑部→督察院→门下省）对所有任务执行，低风险任务也走全套
- **修正**：引入审核分级——🟢低风险跳过审核、🟡中风险督察院一审、🔴高风险完整三级审核
- **原则**：安全与效率平衡，不是所有任务都需要最高级别审核

### 问题：审核部门触发条件不明确
- **发现**：刑部/督察院/门下省角色卡无明确触发条件，导致过度触发
- **修正**：三个角色卡分别添加触发条件，明确🟢🟡🔴对应关系
- **原则**：审核部门的触发条件必须显性化，不能"宁可错杀"

## 自动学习规则（v4.0 新增）

### 自动捕获触发条件

以下情况**必须**写入学习日志（不等用户问）：

| 触发事件 | 记录内容 | 示例 |
|---------|---------|------|
| 任务超时 | 原因 + 下次避免方案 | "工部超时，因为需求太复杂→下次拆成两阶段" |
| 用户纠正 | 纠正内容 + 正确做法 | "用户说不要辩论格式→改为商讨协作格式" |
| 商讨被退回 | 退回原因 + 改进点 | "商讨结果太简单→增加硬产出要求" |
| 执行失败 | 失败原因 + 复盘 | "TTS API调用失败→下次先测试小样本" |
| 用户满意 | 成功模式 + 可复用经验 | "用户喜欢分阶段交付→以后长任务都用里程碑" |

### 规则自进化

同一类问题出现**3次** → 自动生成修正规则：

```
问题：商讨结果总是太简单
出现次数：3
修正规则：商讨必须输出硬产出（第一轮5项、第二轮6项），否则退回重做
```
