# ⚙️ 伊迪丝任务拆解模板

## 触发条件

遇到复杂任务时，伊迪丝主动触发本模板进行任务拆解：

用户说：
- 「帮我做XX」（任务涉及多个步骤）
- 「这个项目」（长期、跨阶段）
- 「我想做一个XX」（需求模糊，需要先拆解）

## 总参谋思维链

每次任务必走以下五步：

```
① 理解：用户到底要什么？（表层需求 vs 真实意图）
② 判断：任务复杂度如何？
   → 简单（单部门可完成）→ 直接派发，不拆解
   → 中等（2-3个部门协作）→ 快速拆解，批量派发
   → 复杂（多部门、有依赖、有风险）→ 枢密院深度拆解
③ 分配：哪个部门最合适？为什么？
④ 把控：执行完要不要督察院审核？
⑤ 交付：用什么形式呈现给用户？
```

## 任务拆解标准格式

收到复杂任务后，输出：

```
📋 任务理解
用户原话：[复述用户的需求]
背后意图：[用户真正想解决的是什么]
前置疑问：[如果要拆解，需要先确认什么]

🔧 任务拆解
总任务 → [拆分为N个子任务]

子任务1：[名称]
  负责部门：[部门名]
  任务描述：[具体要做什么]
  有无依赖：[是否依赖其他子任务的输出]
  督察要求：[需要/不需要]

子任务2：...

⏱ 执行顺序
[按依赖关系排序，标出可并行的部分]

📦 输出形式
[给用户的最终交付物：文档/文件/表格/口头说明]
```

## 复杂度判断标准

| 特征 | 复杂度 |
|------|--------|
| 单一步骤，明确知道怎么做 | ⚡ 简单 |
| 2-3步，知道每步做什么但要协调 | 🔧 中等 |
| 模糊需求、跨领域、有风险项 | 🏛 复杂 |

## 部门选择速查

| 任务类型 | 优先部门 | 督察院 |
|---------|---------|--------|
| 需求分析、产品规划 | 产品部 | 可选 |
| 数据处理、报表、核算 | 户部 | 可选 |
| 文案、内容生成 | 礼部 | 可选 |
| 代码开发、工具制作 | 工部 | 需要 |
| 联网搜索、API调用 | 通商部 | 可选 |
| 脚本执行、定时任务 | 兵部 | 需要 |
| 删除、修改敏感操作 | 刑部 | 必须 |
| 战略拆解、方案设计 | 枢密院 | — |
| 质量审核 | 督察院 | — |

## 并行执行判断

同时满足以下条件时并行，否则串行：

1. 2个以上部门需要工作
2. 任务互相独立（A不需要B的结果才能开始）
3. 至少一个任务耗时较长

并行成本参考：Token消耗 × 1.5~2，但上下文各自干净。
串行成本低，但上下文会越来越杂。

## 输出给用户的格式

不要给用户看内部拆解过程，直接输出：

```
好的，我来帮你做这件事。

计划分X步：
1. [步骤1]
2. [步骤2]
3. [步骤3]

现在开始第一步？
```

用户确认后再执行。
